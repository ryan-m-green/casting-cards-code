# Components Outside the v2 Folder — Inventory & Cleanup Categorization

Working document for deciding which legacy components can be deleted after the v2
migration. Generated by scanning the whole Angular app for component selectors,
walking the component-usage graph upward to the routed pages, and classifying each
page by the shell that owns it.

- **Scope scanned:** `frontend/cast-library-ui/src/app` (everything except `node_modules`)
- **"The v2 folder"** = `src/app/shared/components/v2`
- **"Components outside v2"** = the legacy library under `src/app/shared/components/**`
  (everything that is *not* in `.../components/v2/`). There are **69** such components.
  All other "outside v2" things (`features/**`, `layout/**`, `core/**`) are *pages,
  shells and services* — they are the destinations, not the deletable library pieces.

### How components are reached (important)
Most legacy components are reached **indirectly**:
- Pages render the legacy "cards" (`app-cast-card`, `app-location-card`, `app-faction-card`,
  `app-sublocation-card`), which call `DrawerService.openCastDetail()/openLocationDetail()/…`
  — the **root** drawer then instantiates the legacy `*-detail-content` components.
- The journal library pages call `SubscriptionDrawerService.open()` -> root drawer -> `app-subscription-content`.
- The v2 cards (`cc-cast-card`, `cc-location-card`, …) call the **same** `DrawerService`, so the
  legacy detail drawers are re-used by the v2 shell too.

Consequence: **a component counts as "journal shell" if any journal page can open it, and as
"v2 campaign shell" if any v2 card/component can open it** — even when the component itself
lives outside v2.

## 6. Rules applied & caveats

1. **v2 campaign shell** -> KEEP. Nothing in `shared/components/v2` imports a non-v2 component
   except `icon` (`cc-detail-panel-actions`). The v2 shell's *runtime* reachability of legacy
   components comes through the **global root `DrawerService` drawer** (`app-root` renders it on
   every route) — see the callout in §2.
2. **Journal shell** -> KEEP (everything reachable from a journal page, including the root drawer
   contents the journal library cards open). **Except** components whose only journal presence is
   the **Testarea** page.
3. **Only Testarea, or only v1 campaign shells, or unused** -> DELETE, per the request.
4. "v1 campaign shell" here means **both** the v1 DM shell (`/campaign/:id`) and the v1 player
   shell (`/player/campaign/:id`), since the v2 shell replaces both.
5. Reachability is computed **transitively** through both template selectors *and* the
   `DrawerService`/`SubscriptionDrawerService` calls, which is why some components are listed as
   "found on" a shell even though their folder lives under `shared/components/`.

### Validation / reproducibility
The scan and raw data live in `.tmp-preview/`:
- `selectors.txt` — every component file -> its selector
- `usage-map.txt` — per-component list of files that reference the selector
- `component-analysis.txt` — per-component direct users, resolved page/shell set, and all ancestors
- `analyze.ps1` — the analysis script that produced the above
